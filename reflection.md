# Development reflection — candidate review draft

The hardest part of the workflow was making Review a meaningful checkpoint. A task can be advanced by staff who created it or were assigned to it, but the final decision belongs to a manager. If stage changes and decision recording were separate operations, the dashboard could show a task as closed even if its approval record failed to save. I solved this by putting the permission check, stage transition and audit insert inside a single PostgreSQL transaction with a task row lock. Rejection also saves the manager’s comment in the same transaction. The audit history captures the actor, timestamp and previous and new stages. I verified that staff cannot approve a review and that a manager cannot reject it with a blank comment.

I used OpenAI Codex to build the API and interface, outline the database relationships, and exercise the workflow. One correction was to align the controls with the server’s rules for completed tasks. A completed task is closed for editing, so the interface hides editing and AI confirmation in that state. The server independently checks those rules. AI suggestions use a preview followed by confirmation. I verified that requesting a preview leaves the priority and subtasks untouched, and that attempting to confirm the same suggestion again fails. The mock made this possible without depending on network access or an API key.

One improvement would be to add paginated task lists and an activity view dedicated to each task. For the seeded dataset, fetching all matching tasks and showing the history alongside the details is straightforward. With many offices entering work each day, those lists could grow large. I would add stable pagination ordered by due date and task ID, keep the current filters in the URL, and measure query performance with realistic data before changing the PostgreSQL indexes. This would keep navigation predictable as the number of tasks increases.
